# AI 마케팅 매니저 데이터 수집 및 기획 전략

## 1. 문서 목적

본 문서는 국내 소상공인·중소기업 대상 AI 마케팅 SaaS의 데이터·제품 전략을 정의한다.

초기 기획은 Predis.ai형 콘텐츠 자동화와 Vendasta형 통합 운영 구조를 결합하는 방향이었으나, 제품 목적이 넓고 콘텐츠 생성 자체만으로는 고객이 체감할 경제적 효과를 설명하기 어렵다는 문제가 확인되었다.

따라서 2026-08-13 기준 제품의 중심 가설을 다음과 같이 재정의한다.

> **소상공인의 사업 데이터와 지역 생활 데이터를 분석하여, 이미 존재하지만 놓치고 있는 매출 기회를 발견하고 실제 실행 방법까지 제안하는 AI 서비스**

초기에는 범위를 더 좁혀 **예약형 사업자의 빈 시간·휴면 고객·낮은 재방문 등 미활용 매출 기회를 발견하는 AI 운영 매니저**를 우선 검증한다.

Predis.ai형 콘텐츠 생성과 Vendasta형 CRM·운영 기능은 제품 그 자체가 아니라, 발견한 기회를 실행하고 측정하기 위한 구성요소로 사용한다.

서비스의 핵심 루프는 다음과 같다.

```text
사업 상태·예약·고객·매출
        +
날씨·상권·생활인구·지역 행사
        ↓
숨은 매출 기회 발견
        ↓
AI가 원인과 실행안 제안
        ↓
사용자 승인·수정·거절
        ↓
캠페인·콘텐츠·메시지 실행
        ↓
예약·방문·매출 결과 측정
        ↓
다음 의사결정 개선
```

제품의 장기 비전은 여전히 AI 마케팅 매니저이지만, 첫 제품은 **경제적 문제 하나를 명확하게 해결하는 것**에서 시작한다.

## 1.1 Hospital MVP 구현 검증 현황

2026-08-17 현재 전략의 첫 검증 범위는 Hospital Appointment CSV로 좁혀 구현했다.

- 사업 내부 데이터: 예약 상태·Offering·가명 고객·실제 결제금액
- 관찰: 예약량, 완료, 취소, 노쇼, 실제 완료 매출, 시간대 패턴
- 기회 탐지: LowDemandSlot, RevenueGap, CancellationHotspot, DormantCustomer, ServiceDemandGap
- 우선순위: versioned Opportunity Score
- 실행 루프: manual Recommendation → 사용자 결정 → manual Action → Result → baseline Measurement

현재 시스템에는 실제 AI 호출, 콘텐츠 생성, 외부 채널 실행, 날씨·상권·생활인구 결합이 없다. 따라서 이 문서의 AI·외부 데이터·자동화 항목은 로드맵이며 제공 기능으로 해석하지 않는다. 실제 범위는 `CURRENT_IMPLEMENTATION_STATUS.md`를 따른다.

## 2. 핵심 결론

### 2.1 고객은 AI가 아니라 결과를 구매한다

첫 제품의 가치는 “콘텐츠를 잘 생성한다”가 아니라 다음과 같은 경제적 문제를 줄이는 데 있어야 한다.

- 비어 있는 예약 시간
- 재방문 시기가 지났지만 돌아오지 않은 고객
- 반응이 좋았지만 활용되지 않는 상품·서비스
- 문의는 발생하지만 예약·구매로 전환되지 않는 구간
- 지역 행사·날씨·유동 변화 등 외부 수요 기회를 활용하지 못하는 상황

따라서 제품의 핵심 화면과 지표는 콘텐츠 생성량보다 **발견한 매출 기회, 실행 수, 예약·구매·매출 결과**를 우선한다.

### 2.2 첫 MVP는 예약형 사업자를 우선 검증한다

미용실·네일샵·피부관리·PT·필라테스·사진관처럼 시간 단위의 공급능력과 예약 데이터가 존재하는 업종은 “빈 시간”이라는 손실이 명확하고 결과 측정도 상대적으로 쉽다.

초기에는 여러 업종을 동시에 지원하기보다 1개 업종을 선택해 실제 문제와 데이터 구조를 검증한다.

### 2.3 가입 시 입력은 최소화하고 나머지는 연결·자동 수집한다

사장님이 처음 직접 입력해야 하는 정보는 다음 수준을 목표로 한다.

1. 업종
2. 매장 위치
3. 영업시간
4. 주요 상품·서비스와 가격
5. 현재 가장 해결하고 싶은 문제

예약·매출·고객 데이터는 CSV 또는 외부 시스템 연동으로 가져오고, 날씨·상권·생활인구·지역 행사 등은 위치를 기준으로 자동 결합한다.

### 2.4 공공데이터는 제품의 컨텍스트 계층으로 사용한다

공공데이터 자체는 차별화 자산이 아니므로 핵심 데이터가 아니라 다음 판단을 보조하는 Context로 사용한다.

- 날씨와 예약·방문 수요의 관계
- 시간대·지역별 생활인구 또는 유동 변화
- 지역 행사·축제로 인한 단기 수요 변화
- 주변 업종·상권 구조와 경쟁 강도

실제 API 제공 범위·갱신 주기·이용조건은 구현 시점에 다시 검증한다.

### 2.5 AI의 중심 역할은 Writer가 아니라 Manager다

콘텐츠 생성은 실행 수단이다. 핵심 AI는 다음을 수행해야 한다.

1. 사업 상태를 분석한다.
2. 매출 기회를 발견한다.
3. 왜 기회라고 판단했는지 설명한다.
4. 실행 가능한 행동을 제안한다.
5. 사용자의 결정을 기록한다.
6. 실행 결과를 다음 판단에 반영한다.

### 2.6 효과를 보장하지 말고 측정 가능하게 만든다

서비스는 매출 증가를 일률적으로 보장하지 않는다. 대신 다음 연결을 최대한 정확히 측정한다.

```text
AI가 발견한 기회
→ 제안한 행동
→ 사용자 승인 여부
→ 실제 실행
→ 도달·클릭·문의
→ 예약·구매
→ 연결 매출
```

### 2.7 파인튜닝은 제품 검증 이후에 진행한다

초기에는 API + RAG + 규칙 기반 분석 + 모델 라우팅을 사용한다.

파인튜닝의 우선 대상은 단순 광고 문구가 아니라 충분한 데이터가 축적된 이후의 다음 작업이다.

- 어떤 상황에서 어떤 행동을 추천할지 분류·랭킹
- 업종별 캠페인 유형 선택
- 고객 세그먼트별 재방문 전략
- 반복되는 정책·금칙·형식 검수

### 2.8 장기 핵심 자산은 Decision → Outcome 데이터다

가장 가치 있는 독점 데이터는 다음의 연결 기록이다.

```text
사업 상황
+
외부 상황
+
AI가 발견한 기회
+
AI가 제안한 행동
+
사용자의 결정
+
실제 실행
+
예약·구매·매출 결과
```

이 데이터가 충분히 축적된 후 모델 최적화와 제한적 파인튜닝을 검토한다.

# 3. 제품 데이터 전략의 기본 원칙

## 3.1 고객 데이터 우선

외부에서 수집한 일반적인 마케팅 데이터보다 고객이 직접 제공한 사업 정보와 실제 성과 데이터를 우선한다.

외부 데이터는 시장 상황과 아이디어를 보완하는 데 사용하고, 사업체에 대한 사실은 고객 데이터에서 가져온다.

## 3.2 원본과 가공 데이터 분리

외부 API에서 받은 원본 데이터와 서비스 내부에서 정규화·가공한 데이터를 분리한다.

```text
외부 원본 데이터
    ↓
정규화 데이터
    ↓
분석·추천 데이터
    ↓
AI 입력용 컨텍스트
```

원본 데이터는 장애 복구, 재처리, 감사에 사용하고 정규화 데이터는 서비스 기능에 사용한다.

## 3.3 고객사 간 데이터 격리

각 고객사의 사업 정보, 고객 정보, 콘텐츠, 성과 데이터는 논리적 또는 물리적으로 분리한다.

- 모든 주요 테이블에 `tenant_id` 사용
- 벡터 데이터베이스 컬렉션 또는 네임스페이스 분리
- 캐시 키와 파일 저장 경로 분리
- AI 요청 로그에 고객사 식별자를 직접 노출하지 않음
- 다른 고객사의 원문을 프롬프트에 혼합하지 않음

## 3.4 최소 수집

서비스 기능에 필요하지 않은 개인정보는 수집하지 않는다.

예를 들어 마케팅 성과 분석에 고객 전화번호 원문이 필요하지 않다면, 전화번호 대신 내부 고객 식별자와 문의 유형만 저장한다.

## 3.5 사람의 승인 우선

초기 서비스는 AI가 게시물·광고 예산·고객 메시지를 임의로 실행하지 않도록 한다.

```text
DRAFT
→ AI_REVIEWED
→ USER_APPROVED
→ SCHEDULED
→ PUBLISHED
```

광고 예산 변경, 리뷰 답변, 고객 메시지 발송은 별도의 승인 단계를 둔다.

## 3.6 모델 학습 동의와 서비스 이용 동의 분리

고객 데이터를 콘텐츠 생성에 사용하는 것과 서비스 공통 모델 개선에 사용하는 것은 다른 목적이다.

약관과 동의 화면에서는 다음을 구분한다.

- 서비스 제공을 위한 데이터 처리
- 통계·품질 개선을 위한 가명 데이터 활용
- 모델 파인튜닝을 위한 학습 데이터 활용
- 제3자 AI API 전송
- 외부 채널 API 연동

---


## 3.7 경제적 문제 우선

새 기능은 “숨은 매출 기회를 발견하거나 실제 매출로 전환하는 데 직접 기여하는가?”를 기준으로 MVP 포함 여부를 결정한다.

콘텐츠 생성, 이미지 생성, 캘린더, CRM 등은 독립된 목적이 아니라 문제 해결을 위한 수단으로 본다.

## 3.8 최소 입력·점진적 데이터 연결

가입 시 거대한 설문을 요구하지 않는다. 최소 정보로 첫 분석을 제공하고, 더 정확한 판단에 필요한 데이터는 사용 과정에서 단계적으로 요청한다.

```text
최소 사업 정보
→ 첫 분석
→ 추가 데이터 필요성 설명
→ 예약·매출·고객 데이터 연결
→ 분석 정밀도 향상
```

브랜드 말투, 금지 표현, 경쟁사, 마진율 등은 실제 캠페인 실행 시 필요한 시점에 받는다.

# 4. 수집해야 할 데이터 분류

## 4.1 사업체 기본 데이터

온보딩 데이터는 **필수 입력 / 연결 권장 / 나중에 입력**의 3단계로 구분한다.

### A. 가입 시 필수 입력

| 항목 | 예시 | 사용 목적 |
|---|---|---|
| 업종 | 미용실, 필라테스 | 적용할 기회 탐지 규칙 결정 |
| 매장 위치 | 서울 마포구 합정동 | 공공·상권 데이터 결합 |
| 영업시간 | 월~토 10:00~20:00 | 판매 가능한 시간 계산 |
| 상품·서비스 | 여성컷, PT 10회권 | 어떤 매출이 발생할 수 있는지 파악 |
| 가격 | 30,000원, 500,000원 | 기회 규모와 결과 추정 |
| 현재 목표 | 빈 예약, 재방문, 신규 고객, 객단가 | AI 우선순위 결정 |

### B. 연결하면 가치가 크게 올라가는 데이터

- 예약 내역
- POS·결제·매출 데이터
- 고객 방문 이력
- 상품별 구매 이력
- 과거 캠페인과 프로모션
- Instagram·Meta·네이버·GA4 등 채널 데이터

예약형 업종의 최소 예약 데이터 예시는 다음과 같다.

```json
{
  "reservation_id": "rsv_001",
  "customer_ref": "customer_hash_82",
  "reserved_at": "2026-08-13T14:00:00+09:00",
  "service": "clinic",
  "amount": 80000,
  "status": "completed",
  "visit_type": "returning"
}
```

### C. 필요할 때 추가로 받는 데이터

- 브랜드 말투
- 금지 표현
- 주요 고객층
- 경쟁사
- 마진율
- 직원별 가능한 서비스
- 재고·수용능력
- 특별 프로모션 조건
- 법적 고지·필수 문구

이 데이터는 첫 가입에서 모두 요구하지 않고 실제 추천이나 캠페인 생성 시 필요한 순간에 요청한다.

### 온보딩 원칙

> **입력을 많이 받을수록 좋은 서비스가 아니라, 최소 입력으로 먼저 가치를 보여주고 가치가 확인될수록 데이터를 더 연결하게 만드는 서비스를 목표로 한다.**

## 4.2 브랜드 자료와 내부 문서

고객이 보유한 문서를 업로드받아 브랜드 지식베이스로 사용한다.

### 수집 대상

- 회사 소개서
- 메뉴판과 가격표
- 상품 카탈로그
- 서비스 설명서
- 기존 블로그 글
- 기존 SNS 게시물
- 광고 문구
- 상담 스크립트
- 자주 묻는 질문
- 환불·예약·배송 정책
- 로고와 브랜드 가이드
- 제품·매장 이미지

### 처리 방식

```text
파일 업로드
→ 파일 유형 검사
→ 텍스트·메타데이터 추출
→ 개인정보와 민감정보 탐지
→ 문서 단위 저장
→ 문단 단위 분할
→ 임베딩 생성
→ 고객사별 벡터 저장소 등록
```

초기에는 해당 자료를 모델 재학습에 사용하지 않고 RAG 지식베이스로 사용한다.

## 4.7 외부 시장·검색·공공 데이터

외부 데이터는 콘텐츠 소재보다 **현재 사업 상황을 해석하는 컨텍스트**로 우선 사용한다.

### 공공·생활 데이터 우선 후보

| 데이터 유형 | 예시 | 활용 목적 |
|---|---|---|
| 날씨 | 기온, 강수, 습도, 예보 | 방문·예약 수요 변화 해석 |
| 생활인구·유동 | 시간대별 지역 체류·유입 | 시간대별 잠재 수요 판단 |
| 지역 행사·축제 | 행사 기간, 장소, 유형 | 단기 수요 증가 기회 발견 |
| 상권·업종 정보 | 주변 업종, 점포 변화, 상권 특성 | 경쟁·상권 구조 해석 |
| 공휴일·계절 | 휴일, 방학, 계절 | 반복 수요 패턴 보정 |

### 자동 결합 방식

사용자에게 공공데이터 값을 직접 입력하게 하지 않는다.

```text
매장 주소
   ↓
좌표·행정구역 매핑
   ↓
날씨
+ 생활인구·유동
+ 지역 행사
+ 상권 정보
   ↓
매장 내부 데이터와 결합
```

### 활용 예시

- 평소보다 예약률이 낮지만 주변 유동은 정상 → 수요 부족보다 고객 확보 문제 가능성
- 주변 행사로 단기 유입이 증가하는데 예약은 비어 있음 → 행사 연계 캠페인 후보
- 비 예보가 있고 과거 비 오는 날 방문률이 하락 → 방문 대신 재방문·선결제·배달 등 대체 전략 후보
- 동종업체 증가와 객단가 하락이 동시에 발생 → 단순 할인보다 차별화 전략 검토

공공데이터는 누구나 접근할 수 있으므로 장기 경쟁력 자체로 보지 않는다. 실제 경쟁력은 공공데이터와 고객사의 내부 데이터를 결합해 어떤 행동을 제안했고 어떤 결과가 발생했는지에 있다.

## 4.8 의사결정·결과 데이터

기존의 AI 생성본·수정본뿐 아니라 **사업 상황 → AI 판단 → 사용자 결정 → 실행 → 결과** 전체를 저장한다.

```json
{
  "opportunity_id": "opp_001",
  "tenant_id": "tenant_001",
  "opportunity_type": "idle_capacity",
  "evidence": {
    "reservation_rate": 0.38,
    "period": "tuesday_14_17",
    "external_context": "normal_local_demand"
  },
  "recommendation": {
    "segment": "60_120_day_dormant",
    "campaign": "weekday_reactivation",
    "channel": "kakao"
  },
  "user_decision": "approved",
  "result": {
    "reservations": 7,
    "revenue": 490000
  }
}
```

반드시 보존할 핵심 항목:

- 어떤 문제가 감지되었는가
- 어떤 근거로 기회라고 판단했는가
- AI가 무엇을 제안했는가
- 사용자가 승인·거절·수정했는가
- 거절 사유는 무엇인가
- 실제로 실행되었는가
- 예약·구매·매출 결과는 무엇인가
- 같은 유형의 다음 추천 결과가 개선되었는가

# 5. 데이터 수집 경로

## 5.1 수동 입력·CSV 업로드

MVP에서는 외부 시스템 연동보다 **최소 입력 + CSV 업로드**를 우선한다.

### 직접 입력

- 업종
- 주소
- 영업시간
- 주요 상품·서비스
- 가격
- 현재 목표

### 우선 업로드

- 최근 3~6개월 예약 데이터
- 가능하면 결제·매출 데이터
- 고객 방문 이력

### 선택 업로드

- 기존 콘텐츠
- 이미지·로고
- 브랜드 규칙
- 과거 프로모션

### 원칙

- 첫 가치 확인 전에 긴 온보딩 설문을 요구하지 않는다.
- CSV 템플릿을 제공해 예약 데이터를 쉽게 가져오게 한다.
- 필수 컬럼이 부족하면 분석 가능한 범위와 부족한 항목을 명확히 설명한다.
- 고객 식별자는 가능하면 내부 ID 또는 가명값으로 처리한다.

## 5.2 공식 API 연동

API 연동은 고객이 계정을 연결하고 접근 권한을 명시적으로 허용한 경우에만 진행한다.

| 연동 대상 | 수집 가능 데이터 | 권장 단계 |
|---|---|---:|
| GA4 Data API | 웹·앱 사용자, 페이지, 이벤트, 전환, 매출 | 2단계 |
| Google Business Profile | 사업장 정보, 리뷰, 성과 보고서 | 2단계 |
| 네이버 검색광고 API | 광고 계정·캠페인·성과 보고서 | 2~3단계 |
| 네이버 커머스 API | 스마트스토어 상품·주문 등 | 쇼핑몰형 2단계 |
| 카카오톡 채널 API | 채널 관계, 고객파일 관리 | 3단계 |
| 카카오모먼트 API | 광고·메시지 광고 운영 | 3~4단계 |
| Meta/Instagram | 게시·인사이트·광고 데이터 | 2~3단계 |
| Google Ads | 캠페인·광고·비용·전환 | 3~4단계 |

Google Analytics Data API는 GA4 보고서 데이터를 프로그래밍 방식으로 조회하고 대시보드·자동 보고서·다른 업무 시스템과의 연동에 사용할 수 있다.[^1]

Google Business Profile API는 사업장 계정과 위치 정보를 관리하며 리뷰와 성과 데이터용 API를 별도로 제공한다.[^2]

네이버 검색광고 API는 광고주센터에서 API 라이선스와 비밀키를 발급받아 사용한다.[^3]

네이버 커머스 API는 커머스 API 센터에서 애플리케이션 등록과 인증 절차를 거쳐 스마트스토어 주요 기능을 연동한다.[^4]

카카오톡 채널 API는 채널 추가 관계 조회와 고객파일 관리 기능 등을 제공하지만, 일반적인 대량 메시지 발송 기능과 동일한 API가 아니다. 메시지 광고 기능은 카카오모먼트 측 권한과 비즈니스 설정이 별도로 필요하다.[^5][^6]

## 5.3 웹 검색 API

최신 뉴스, 트렌드, 지역 행사, 공개 경쟁 정보를 조사할 때 사용한다.

### 원칙

- 콘텐츠 생성 시 최신성 검증
- 원문 전체가 아니라 요약·특징·링크 메타데이터 저장
- 저작권 또는 이용약관에서 금지한 방식으로 수집하지 않음

## 5.4 크롤링

크롤링은 공식 API나 고객 제공 방식으로 해결할 수 없는 경우에만 제한적으로 검토한다.

### 크롤링 전 확인 항목

- 로그인 또는 우회 접근이 필요한지

- 데이터 사용 목적과 보존 기간
- 공식 API 또는 제휴 방식이 존재하는지

### 하지 말아야 할 방식

- 로그인 쿠키를 받아 비공개 화면 수집
- CAPTCHA 우회
- 차단 회피를 위한 프록시 순환
- 개인 계정 프로필 대량 수집
- 리뷰 작성자 이름과 프로필을 불필요하게 보관
- 경쟁사 글과 이미지를 그대로 복제해 콘텐츠 생성
- 채널의 비공개 분석 데이터를 무단 수집

# 6. 채널별 현실적인 수집 전략

채널 연동은 첫 제품의 정체성이 아니라 **발견한 매출 기회를 실행하고 성과를 회수하기 위한 실행 계층**이다. 초기 MVP에서 모든 채널을 지원하지 않으며, 선택한 업종의 실제 고객 접점에 따라 우선순위를 정한다.

## 6.1 네이버 블로그

### MVP

- 고객이 기존 글 URL 또는 텍스트를 등록
- 고객이 내보낸 글 목록을 CSV로 업로드
- 제목·본문·게시일·카테고리 분석
- AI가 글을 생성하고 사용자가 직접 발행
- 발행 후 URL을 서비스에 등록

### 확장

- 공식 제공 범위 또는 제휴 가능성 검토
- 검색 결과 기반 노출 추적
- 네이버 검색광고 데이터와 결합
- 블로그 유입을 GA4 또는 랜딩 페이지에서 추적

### 주의

네이버 블로그 자동 게시와 상세 성과 수집은 일반 공개 API만으로 제품이 요구하는 전체 기능을 구현하기 어려울 수 있다. 서비스 기획 단계에서 자동 발행을 확정 기능으로 간주하지 말고, **복사·발행 보조 또는 브라우저 확장 기능**을 대안으로 둔다.

## 6.2 네이버 플레이스

### MVP

- 사업장 정보 직접 입력
- 리뷰 CSV 또는 수동 등록
- 리뷰 답변 초안 생성
- 사용자가 복사해 답변
- 월간 리뷰 요약

### 확장

- 공식 파트너·제휴·제공 API 범위 확인
- 리뷰와 플레이스 성과 자동 수집
- 리뷰 요청 캠페인
- 긍정 리뷰의 콘텐츠 재활용

### 주의

플레이스 리뷰 자동 수집·답변·발행을 핵심 전제로 개발하기 전에 공식 접근 권한과 허용 범위를 반드시 확인한다.

## 9.1 동기화 방식

| 데이터 | 권장 방식 |
|---|---|
| 예약·주문·결제 | 웹훅 우선, 없으면 CSV·주기 동기화 |
| 고객 방문 이력 | 일 단위 또는 이벤트 기반 |
| 콘텐츠·광고 지표 | 1일 1~4회 배치 |
| 사업장 정보 | 일 1회 또는 수동 |
| 리뷰 | 수시간~1일 간격 |
| 날씨 | 분석·캠페인 필요 시 예보 갱신 |
| 생활인구·유동 | 제공 주기에 맞춘 배치 |
| 지역 행사 | 일·주 단위 |
| 상권·업종 정보 | 주·월 단위 또는 온보딩 시 |

실시간성이 제품 가치에 직접 영향을 주지 않는 데이터는 과도하게 자주 호출하지 않는다.

# 10. AI 활용 전략

## 10.1 초기: 규칙·통계 + RAG + LLM

모든 판단을 LLM에 맡기지 않는다.

초기 구조는 다음과 같이 역할을 분리한다.

```text
정형 데이터 계산
→ 규칙·통계 기반 기회 후보 탐지
→ 고객사 RAG 컨텍스트 결합
→ LLM이 원인 설명·우선순위·실행안 생성
→ 사용자 승인
```

예약률, 공석률, 재방문 기간, 매출 합계, 캠페인 전환율 등 계산 가능한 값은 코드로 계산한다.

## 10.2 AI Manager의 역할

AI Manager는 다음 입력을 조합한다.

```text
현재 사업 상태
+ 예약·고객·매출 데이터
+ 과거 승인·거절 이력
+ 과거 실행 성과
+ 브랜드·상품 정보
+ 지역·날씨·행사 컨텍스트
```

그리고 다음을 출력한다.

1. 발견한 매출 기회
2. 근거와 불확실성
3. 예상되는 영향 범위
4. 권장 고객 세그먼트
5. 권장 채널·상품·시간
6. 실행용 콘텐츠·메시지
7. 측정해야 할 성공 지표

## 10.3 고객사별 선호·운영 규칙 학습

사용자의 반복적인 승인·수정·거절 패턴을 요약한다.

```json
{
  "tenant_id": "tenant_001",
  "learned_preferences": [
    "가격 할인보다 서비스 추가 혜택 선호",
    "화요일 오후에는 펌 캠페인 제외",
    "휴면 고객 메시지는 90일 이후에만 제안",
    "카카오 메시지는 월 2회 이하"
  ]
}
```

이 규칙은 AI가 임의로 확정하지 않고 사용자가 확인·수정할 수 있도록 한다.

## 10.4 성과 기반 추천

새로운 기회가 발견되면 과거의 유사한 상황과 결과를 우선 검색한다.

- 같은 고객사
- 같은 업종
- 같은 기회 유형
- 같은 요일·시간대
- 유사한 고객 세그먼트
- 유사한 상품·가격대
- 유사한 외부 상황
- 실제 예약·매출 결과가 존재하는 실행

## 10.5 모델 파인튜닝 시점

다음 조건이 충족되기 전에는 파인튜닝을 우선하지 않는다.

- 동일한 의사결정 유형 데이터가 충분히 누적됨
- 입력·출력 스키마가 안정됨
- 추천과 결과의 연결이 신뢰할 수 있음
- 사람의 승인 품질이 일정함
- 데이터 사용 동의가 명확함
- RAG·규칙·프롬프트만으로 해결하기 어려운 반복 문제가 확인됨
- 비용 또는 품질 개선 효과를 측정할 수 있음

### 우선 파인튜닝 후보

- 기회 유형 분류
- 캠페인 전략 랭킹
- 고객 세그먼트별 행동 추천
- 업종별 메시지 스타일 변환
- 반복되는 금칙·정책 검사

### 초기 파인튜닝에 부적합한 작업

- 최신 지역·시장 정보 판단
- 사실 확인이 필요한 분석
- 소수 고객 데이터만 존재하는 전략 추천
- 매출 증가 자체를 예측·보장하는 모델
- 고객사마다 수시로 변하는 상품·가격 정보

- 데이터 학습 활용은 별도 동의

개인정보보호위원회는 개인정보 처리방침에 법률상 요구되는 처리 기준과 절차를 투명하게 작성하도록 2026년 작성 지침을 제공하고 있다.[^8]

가명정보를 활용하더라도 재식별 위험, 처리 목적, 결합 가능성, 안전조치와 적정성 검토가 필요하다.[^9]

## 13.2 외부 AI API 전송 전 처리

원문이 꼭 필요한 경우에만 제한적으로 전송하고 요청 로그의 보존 범위를 설정한다.

# 18. 제품 기획 권고안

## 18.1 핵심 제품 정의

> **소상공인이 이미 가지고 있는 예약·고객·매출 데이터와 지역 생활 데이터를 분석해, 놓치고 있는 매출 기회를 찾아주고 실제 행동까지 연결하는 AI 서비스**

마케팅 콘텐츠는 제품 목적이 아니라 행동 실행 수단이다.

## 18.2 첫 번째 제품 가설

> 예약형 사업자가 최근 3~6개월 예약 데이터를 연결하면, AI가 반복적으로 비는 시간과 휴면 고객을 찾아 사장님이 이해할 수 있는 금액·근거와 함께 보여줄 수 있다.

측정 지표:

- 첫 기회 발견까지 걸리는 사용자 입력 단계
- 유효 기회 발견률
- 기회 설명 이해도
- 기회 채택률

## 18.3 두 번째 제품 가설

> AI가 발견한 기회에 맞춰 고객 세그먼트·상품·채널·시간·문구를 함께 제안하면, 단순 콘텐츠 생성보다 실제 실행률이 높아진다.

측정 지표:

- 추천 채택률
- 승인 후 실행률
- 캠페인 제작 시간
- 거절 사유

## 18.4 세 번째 제품 가설

> 실행 결과를 예약·구매·매출과 연결하면 일반적인 생성형 AI보다 다음 추천의 품질을 지속적으로 개선할 수 있다.

측정 지표:

- 결과 연결률
- 예약 전환율
- 재방문 전환율
- 공석 개선률
- 기회당 연결 매출
- 유사 상황에서의 추천 성과 개선

## 18.5 공공데이터 활용 가설

> 날씨·생활인구·지역 행사·상권 데이터를 내부 예약·매출 데이터와 결합하면 내부 데이터만으로는 설명하기 어려운 단기 수요 변화와 캠페인 타이밍을 더 잘 해석할 수 있다.

공공데이터의 효과는 별도로 검증하고, 실제 성과 개선이 확인되지 않는 데이터 소스는 제거한다.

## 18.6 대행사 확장 가설

> 대행사는 AI 생성 기능보다 여러 고객사의 “발견된 기회 → 승인 → 실행 → 결과”를 한곳에서 관리하고 보고하는 데 더 큰 가치를 느낄 수 있다.

따라서 멀티테넌시와 권한 구조는 초기 데이터 모델부터 유지하되, 대행사 전용 화면은 제품 검증 이후 확장한다.

서비스의 장기 경쟁력은 특정 LLM이나 공공데이터 자체에 종속되지 않는다.

가장 중요한 자산은 다음 네 가지다.

1. 고객사별 구조화된 사업·예약·고객·매출 데이터
2. 어떤 상황에서 어떤 매출 기회를 발견했는지에 대한 기록
3. AI가 제안한 행동과 사용자의 승인·거절·수정 데이터
4. 실제 실행과 예약·구매·매출 결과가 연결된 `Decision → Outcome` 데이터

따라서 첫 개발 단계에서 우선 완성해야 하는 것은 다음이다.

1. **한 업종의 경제적 문제 정의**
2. **최소 입력과 예약 데이터 수집**
3. **기회 탐지 로직**
4. **AI의 설명·실행 제안**
5. **사용자 결정 기록**
6. **성과 연결**
7. **고객사 데이터 격리**

콘텐츠 생성, 이미지 생성, 멀티모델 라우팅, 자동 발행, 파인튜닝은 위 폐쇄 루프를 강화할 때 순차적으로 추가한다.
